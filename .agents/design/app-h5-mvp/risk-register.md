# App H5 白标 MVP：风险登记表

> 任务：S1-01
> 日期：2026-09-13
> 原则：一期优先保证可运行和可回滚；高风险项先记录，未经明确确认不修改。

| ID | 风险 | 等级 | 触发条件 | 影响 | 一期处理 |
|---|---|---:|---|---|---|
| R-01 | 独立 WebView 初始无登录 Cookie | P0 | APP WebView 与管理端/浏览器 Cookie 隔离 | H5 未登录或登录循环 | 一期固定使用一次性 authCode 换取 H5 HttpOnly Cookie；H5/API 保持同源 |
| R-02 | 动态 `/app/*` 仍进入平台 Layout | P0 | 只新增页面，未改 Layout 分流 | 业务方看到平台导航、弹窗和请求 | 独立 Layout + 路由级分流 |
| R-03 | 只在前端做 AppKey/权限判断 | P0 | H5 直接调用现有 API | 越权读取 App 或 Chat 数据 | 服务端解析 AppKey，并继续调用现有 `authApp`/Chat 鉴权 |
| R-04 | 直接复制 Chat 逻辑 | P1 | 为了快速做 H5 复制 ChatWindow/Context | 后续修复分叉、状态不一致 | 复用现有 Chat Context、初始化和流式 API，只增加适配层 |
| R-05 | 将内部 App ID 放到业务 URL | P1 | 使用 `/app/<appId>` | 暴露内部 ID，未来迁移 URL 失效 | 使用业务 `appKey -> appId` 映射 |
| R-06 | APP 登录态通过长期 Token URL 传递 | P0 | `/app/*?token=...` | Token 泄露、历史记录和日志暴露 | 使用同源 Cookie 或一次性 authCode |
| R-07 | authCode 被重复消费 | P0 | APP 免登录桥接未做幂等 | 登录态伪造或重复换取 | code 短时效、单次消费、绑定用户/AppKey/设备，可审计 |
| R-08 | 开放重定向 | P0 | 直接信任 `returnTo`/`lastRoute` | 钓鱼和 Token 泄露 | 只允许同源 `/app/*` 白名单路径 |
| R-09 | H5 错误暴露内部服务名 | P1 | 直接透传服务端错误 | 暴露容器、数据库、内部域名 | AppEntry 错误边界和 API 脱敏 |

| R-11 | 页面 title/favicon 被全局 Head 覆盖 | P1 | `useInitApp` 和页面 Head 同时渲染 | 用户仍看到平台名称或错误图标 | AppEntry 路由使用专属 Head 优先级并验证 DOM |
| R-12 | JS Bundle 中仍存在内部标识 | P2 | 后续业务方升级为源码/Bundle 检查 | 严格白标验收失败 | 当前不作为业务验收项；保留后续源码级白标任务 |

| R-15 | 数据库/Redis/Bucket 名称重命名 | P0 | 批量改 `fastgpt` 前缀 | 历史数据、缓存、存储和迁移不兼容 | 不纳入 MVP，保留兼容映射 |
| R-16 | 部署服务名修改遗漏依赖 | P2 | 内部后续要求运行资源白标 | 服务间 DNS、NO_PROXY、healthcheck 失败 | 业务方不交付 Docker，一期不改；后续单独运维变更 |
| R-17 | 生产镜像仅重新命名但元数据仍暴露来源 | P2 | 业务方检查 Docker history/SBOM | 严格供应链白标失败 | 一期定义为运行资源白标；源码/供应链白标后置 |

## S1-01 结论

当前没有发现必须立即修改现有内部协议才能完成 H5 MVP 的问题。最大阻塞风险是：

1. H5/API 是否同源。
2. APP 是否需要已有登录态换取 H5 登录态。
3. 业务方是否检查部署和 WebView 网络层。
4. 是否允许部署层单独重命名运行资源。

| ID | 风险 | 等级 | 影响 | 处理 |
|---|---|---:|---|---|
